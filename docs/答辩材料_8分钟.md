> 使用方式：本文件既是讲稿，也是 PPT 大纲。每节标出的「幻灯片」对应一页，方括号内为时间预算，正文为口述稿（按每分钟约 190 字控制）。

## 幻灯片 1 · 封面（0:00—0:20）

**页面要点**：项目名、副标题「基于 MongoDB 的数据建模、应用实现与高可用架构演进」、姓名学号、日期。

**口述**：
各位老师好，我是数据科学与大数据技术专业的何铭轩，本次汇报《智慧图书馆数字资源平台》。项目在本人电脑的 Docker 环境里真实跑通，从单机到三节点副本集再到两分片集群，全部留有运行日志与截图。

## 幻灯片 2 · 业务与数据约束（0:20—1:10）

**页面要点**：三类约束（数据形态 / 访问模式 / 环境）+ 数据基线 50 / 30 / 3000。

**口述**：
先说我面对的是什么数据。书目 50 条，其中有 4 条整段缺 tags、47 条缺电子书名；读者 30 条，2 条缺偏好分类；借阅流水 3000 条，覆盖 2023 年 1 月到 2025 年 12 月共 37 个月。
这些数据有两个特点：一是结构不齐，书目里有标签数组和馆藏位置这样的嵌套；二是查询维度多，既要按类别加价格区间组合筛选，也要按学院、按年月做聚合。
环境约束更硬：只能在一台开发机上做，且本机已有 MongoDB 容器和两套业务容器不能动。所以我全部新开容器，端口改用 27018、27101 起、27201、27301 起和 27030，统一接入自建网络，只绑 127.0.0.1。

## 幻灯片 3 · 技术选型（1:10—2:10）

**页面要点**：四方案对比表（MongoDB / MySQL / Redis / HBase）+ 两个 CAP 场景 + BASE 边界。

**口述**：
选型不是选最快的，而是选最合适的。关系型能满足强一致，但书目的嵌套结构要么拆表、要么塞 JSON 列丧失索引；Redis 不能当主存；HBase 在本机部署成本过高。文档型在数组索引、聚合管道和原生分片上正好对上我们的三个需求，所以选它。
CAP 我没有给整个系统贴标签，而是分了两个场景：馆藏检索、评分榜允许秒级陈旧，走 AP，读偏好设成从优先；借阅流水写入和库存扣减不能丢，走 CP，写关注要求多数派、读走主节点。
BASE 的边界也一样清楚：统计结果可以重算，允许最终一致；流水、库存、审计日志不能重算，必须强一致。

## 幻灯片 4 · 数据模型（2:10—3:10）

**页面要点**：集合结构图 + 字段类型表 + 五条关键决策。

**口述**：
全库 6 个集合。这里重点讲四个容易选错的地方。
第一，日期用 BSON Date 不用字符串，因为趋势统计要用按年按月聚合，字符串排序在混合格式下会失效。
第二，库存用 Int32 不用浮点，避免加一之后出现 3.0 和 3 比较的歧义。
第三，馆藏位置嵌套不拆表，因为位置随书不变、调整是单文档原子更新；只有要按书架盘点、或一本书对应多个独立借还的馆藏点时才该拆。
第四，日志用定长集合，只追加、只留最近一万条、不需要索引；而借阅流水必须是普通集合，因为它要建四类索引、还要更新归还时间、将来还要分片——定长集合三样都做不到。

## 幻灯片 5 · 单机功能与索引（3:10—4:10）

**页面要点**：15 项菜单截图 + 索引前后对比表（2.29 倍 / 48.89 倍）。

**口述**：
功能上做了 15 项菜单：五类检索、四类统计、借还书、文件上传下载、日志与总览。检索结果与源数据逐条核对一致。
最有说服力的是索引这一块。借阅流水按读者查询，扫描文档数从 3000 降到 10，200 次平均耗时从 1.949 毫秒降到 0.850 毫秒。
但我不拿这个数字当结论，因为 3000 条数据全在内存里，毫秒级差异是噪声——50 条图书那组甚至出现了 0.92 倍的「变慢」。所以另建了 20 万条放大集合，同一类查询从 42 毫秒降到 0.9 毫秒，提速 48.89 倍，这个才站得住。

## 幻灯片 6 · GridFS 与权限（4:10—4:50）

**页面要点**：6 个文件字节校验 + 三账号权限矩阵。

**口述**：
电子书和封面走 GridFS。理由是单个文档上限 16 MB、整体读写会把文件全读进内存、而且内容和元数据混在一起没法按书名检索。6 个文件上传后按书名下载，做了三方字节比对：下载数、库记录数、源文件数，全部一致。
权限上三个账号都建在 admin 库：只读、读写、管理。验证脚本逐一试了 7 类操作，只读账号连写日志都被拒，读写账号不能看服务器状态也不能建用户。这里踩过一个坑：listDatabases 普通账号也能用，拿它验证权限会得出错误结论，必须换成 serverStatus。

## 幻灯片 7 · 副本集与故障转移（4:50—6:00）

**页面要点**：三节点拓扑 + 五种读取偏好实测 + 故障时间线 + 179 次零失败。

**口述**：
副本集三个节点，优先级 2 比 1 比 1，正常情况下第一个节点是主。五种读取偏好我逐个实测了落点：主优先落在主节点，从偏好落在第二台，就近读落在延迟最低那台。
故障演练是这样做的：起一个每半秒写一次的探针，然后停掉主节点。结果是 1 秒内完成选主，第二台节点接任；原主重启后先做从节点追日志，随后按优先级把主位夺回来。
整个 90 秒里 179 次写入、179 次读全部成功，最长一次写入 20.7 毫秒是首次建连，P99 只有 2.8 毫秒。也就是说，对业务是基本无感的。
这里我要如实说明一次返工：第一次演练的探针脚本把字符串当读偏好传进去，启动就崩了，记录是空的；改成读偏好对象重跑，才有这 179 条有效样本。

## 幻灯片 8 · 分片集群与收尾（6:00—7:20）

**页面要点**：集群拓扑 + 分布 43.3% : 56.7% + 分片键三方案对比 + 局限。

**口述**：
分片集群是配置服务器加两个分片加一个路由。只对借阅流水分片，分片键用读者卡号的哈希值。
为什么不用时间或书号？按时间分片，新写入永远落在最后一块，是典型的写热点；按书号分片，热门书的读写都会挤到同一个块；哈希卡号之后，3000 条流水在两个分片上分布是 43% 比 57%，各两个块，没有大块。
代价是按书号、按时间查会变成跨分片。实测定向查询 0.71 毫秒，跨分片 1.50 毫秒，是 2.1 倍。在 3000 条上只差 0.8 毫秒，但数据涨到千万级时，这个差距会体现在网络往返和合并排序上，所以分片键的取舍必须按真实查询分布来定。
最后说局限：配置服务器和分片都还是单节点，生产要三节点；所有容器在同一台机器上，故障域没有隔离；数据量太小，看不到块分裂和迁移；口令还是明文配置。这套东西验证的是可行性和演进路径，不能直接当生产方案。

## 附：可能被追问的问题与应答要点

| 问题 | 应答要点 |
|---|---|
| 为什么不用关系型数据库？ | 书目嵌套与数组标签是主因；关系型要拆 3—4 张表并多次 join，统计还要额外建汇总表。 |
| 分片键能改吗？ | 只能通过 refineCollectionShardKey 追加后缀，主键不能换；要换只能重建集合迁移数据，所以选键必须前置论证。 |
| 副本集切换为什么这么快？ | 收到停止信号后主节点先优雅降级，两个从节点心跳超时即发起选举，priority 高者优先；本项目实测 1 秒内完成。 |
| 写入零失败是数据没丢吗？ | 写关注 majority，驱动可重试；探针写入逐条成功，事后核对条数与 179 条一致。 |
| 统计结果和流水为什么对不上？ | 图书字段 borrow_count 是历史累计，流水只覆盖三年；文档中保留两种口径并注明来源。 |
| 定长集合为什么不能分片？ | capped 集合不支持删除与更新，也不支持分片，只能在单节点上定长滚动。 |
| 这套方案能上生产吗？ | 不能直接上：配置服务器与分片需扩为三节点、密钥要托管、需压测事务与备份恢复。文档 6.5 节已列全。 |
| 数据量这么小，索引结论可信吗？ | 小集合结论只写扫描量；耗时结论来自 20 万条放大集合，且说明了放大方法与退出条件。 |
